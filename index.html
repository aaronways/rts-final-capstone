01 · Overview

What this system does

A radar return arrives as a hardware interrupt. The ISR does the minimum legal work — timestamp, debounce, signal — and hands the actual response to a lower-priority task, while four periodic avionics tasks keep meeting their deadlines on the same core. The question the bench answers is what delays that response: the signaling mechanism, or the priority ladder.

Configuration under test

  • Button on GPIO 18, internal pull-up, negative-edge interrupt, 200 µs debounce gate.
  • IRAM_ATTR ISR raises a scope pulse on GPIO 19, timestamps entry, and signals two bottom halves — one binary semaphore, one direct task notification — so the two paths can be compared on the same event.
  • Both bottom-half tasks at priority 12, pinned to Core 1.
  • Four periodic load tasks pinned to Core 1 on a rate-monotonic ladder: priorities 15 / 10 / 5 / 2 at periods 100 / 200 / 500 / 1000 ms.
  • Compile-time switches: WITH_LOAD brings the load fixture online, BREAK_YIELD removes the context-switch request from the ISR.

The priority geometry is the point. Only load task A at priority 15 outranks the bottom halves; B, C and D at 10, 5 and 2 do not. So exactly one task in the fixture can delay a wake, and its cost is bounded by its own execution time.

Tailoring

Built toward embedded and avionics software roles, which is why the deliverable is evidence rather than features: a schedulability argument, three independent timing instruments, a hazard table mapped to recognised standards, and a fault-injection result reported as measured rather than as hoped.

03 · Architecture

Concurrency and preemption

Core 1 timeline, idle baseline against the loaded case.

Control flow is one hop. The GPIO edge fires the ISR, which timestamps entry into isr_entry_time_us, gates on debounce, then issues both xSemaphoreGiveFromISR and vTaskNotifyGiveFromISR before requesting a context switch. Each bottom half unblocks, reads the shared entry timestamp, computes its own wake latency, updates a running maximum, and logs. Nothing else crosses between the interrupt and task contexts.

One caveat the diagram does not show. gpio_install_isr_service() is called from app_main, which runs on Core 0, so the interrupt is allocated on Core 0 while both bottom halves are pinned to Core 1. Every wake in this build is therefore a cross-core wake. That detail does not change the priority argument — the bottom halves still contend with the load fixture on Core 1 — but it is the reason the fault injection in section 05 produces no visible failure.

Engineering analysis

1 · What is in the ISR, and what is not

Kept. esp_timer_get_time() for the entry timestamp — ISR-safe, and both the debounce gate and the latency measurement depend on it. The debounce comparison against last_edge_us, which must run before signaling or one press becomes several events. The writes to isr_entry_time_us and presses_observed, single words that the bottom halves read. The BaseType_t higher_woken flag required by the FromISR API. The two FromISR signal calls, which are the ISR's actual job and the only ISR-safe variants. And portYIELD_FROM_ISR, which requests the context switch on return.

Removable. The two gpio_set_level calls on GPIO 19 are pure instrumentation. They cost roughly 13 µs of pulse width and would come out of a shipping build.

Deliberately absent. No printf or ESP_LOGI — logging takes a UART mutex, and taking a mutex from interrupt context is undefined behaviour. No allocation, no blocking calls, no vTaskDelay, no bus transactions. All of that lives in the bottom half, which is the entire reason the pattern exists.

2 · Binary semaphore against direct task notification

The reported maxima say notification wins by a wide margin — 30 µs against 2560 µs idle. That comparison does not survive inspection, and the instrumentation is why.

Both bottom halves subtract from a single shared isr_entry_time_us. They sit at equal priority, so they run in sequence, and whichever runs second has the first one's ESP_LOGI — a UART transmission — sitting inside its measured window. The idle run makes this unambiguous: notification holds 20–30 µs across all 51 presses while the semaphore column scatters across 915, 1138, 2381, 2387, 2537 and 2560 µs. A genuine mechanism cost would be roughly constant, not spread over a 1.6 ms range on an otherwise idle core. At hits #49 and #50 of the loaded run the order flips, and notification becomes the path reading 2246 µs while the semaphore reads 151 and 416 µs.

Conclusion. Real wake latency is 20–30 µs on both paths, and the difference between them is below this instrument's noise floor. Direct notification should still be cheaper in principle — it writes the target task's notification value directly rather than going through a separate queue object — but this bench cannot demonstrate that, and claiming an 85× advantage from these numbers would be wrong. Resolving it needs per-path timestamps and the log moved outside the timed window.

3 · Latency under load, and which task is responsible

Notification's worst case goes from 30 µs idle to 2692 µs loaded, about 90×. The obvious reading is that load task A causes it, since A at priority 15 is the only fixture task that outranks the bottom halves at 12. The measured WCET refutes that. A's execution time is 346 µs. One instance of A cannot produce a 2692 µs delay; it is short by a factor of about eight. B, C and D at priorities 10, 5 and 2 cannot preempt the bottom halves at all, so they contribute nothing to the blocking term.

So the worst-case blocking the load fixture can inflict is bounded by CA = 346 µs, and the remaining ~2.3 ms is the same print-order contamination described above — it appears in the loaded run for the same reason it appears idle.

Independent evidence the ladder behaves as designed. Under press activity the measured times for B, C and D inflate — B from 15238 to 23315 µs, C from 33368 to 41887, D from 100011 to 108528 — while A stays at exactly 346 across four separate runs. That asymmetry is the priority ordering made visible: MEASURE_WCET brackets wall-clock time, so for B, C and D it captures preemption by the priority-12 bottom halves as though it were execution. A is never preempted by anything in this system, so its figure is a true WCET while the others are response times with interference included. The quiescent values are the ones reported in the table.

4 · Induced failure

Covered in section 05.

Two instruments, two different windows

The 15.35 µs from the logic analyzer and the 20–30 µs from the serial log measure different things and should not be expected to match. The analyzer spans button edge to ISR pulse: hardware edge detection, the debounce comparison, and the ISR prologue. The serial figure spans ISR entry to the bottom half actually running. The first is interrupt response; the second is wake latency.

The analyzer figure repeats to the hundredth of a microsecond across three presses because the simulator models the interrupt entry path with fixed timing. On silicon this would be a distribution, widened by cache state, bus contention and pipeline effects. The precision here is a property of Wokwi, not evidence of a deterministic interrupt path.

05 · Fault injection

Removing the yield

Build with BREAK_YIELD 1 and the ISR returns without requesting a context switch, after a FromISR call that set higher_woken.

Rule broken. Omitting portYIELD_FROM_ISR(higher_woken) after a FromISR primitive reported that a higher-priority task became ready.

Predicted. The wake is delivered but not acted on until the next scheduler tick, turning a microsecond-scale response into a millisecond-scale one.

Observed. No change. Per-press latency stayed at 24–30 µs, and the reported maximum stayed at 2692 µs — identical to the build with the yield intact.

They do not match, and the reason is core placement. The ISR is allocated on Core 0 because gpio_install_isr_service() runs from app_main, while both bottom halves are pinned to Core 1. A local yield request only affects the core the ISR is running on. Waking a task on the other core does not use it — ESP-IDF raises an interprocessor interrupt against Core 1, and Core 1 reschedules whether or not portYIELD_FROM_ISR was called. In this configuration the line is dead code, which is why removing it changes nothing.

How to make the failure visible. Install the ISR service from a task pinned to Core 1 so the interrupt and its bottom halves share a core. The yield then governs the wake, and removing it should defer the response to the next tick. Predicted but not yet measured — the build on this site keeps the original Core 0 placement, and this is the first thing I would test next.

08 · Reflection

Looking back

Draft below, built from what actually happened during this build. Rewrite it in your own voice before you ship — this is the section a reader will most easily tell you did not write.

What I would do differently

Instrument once, correctly, instead of interpreting around a flawed measurement. Both bottom halves share one entry timestamp and log inside the timed window, and that single decision cost me the comparison the application exists to make. I spent more effort explaining why the semaphore number was not real than it would have taken to latch two timestamps and move the print. I would also have checked that the documented periods matched the code before building an analysis on them — the comments say 10 / 20 / 50 / 100 ms and the firmware says 100 / 200 / 500 / 1000, a factor of ten that would have made my utilization figure 2.46 and the whole task set infeasible.

What was harder than expected

Trusting arithmetic over a story that already sounded right. My first analysis attributed a 2692 µs delay to the priority-15 load task, which is a clean explanation and fits the priority ladder exactly. Then I measured that task's execution time at 346 µs and the explanation stopped being possible. The number I had been most confident about was the one that was wrong, and nothing about the reasoning felt weak until it was checked against a measurement.

The most valuable thing I learned

A measurement is a claim about a specific window, and most of the work is knowing which window. The logic analyzer reads 15.35 µs and the serial log reads 20–30 µs for what I was loosely calling the same thing, and both are correct because they bracket different events. Same lesson in the fault injection: removing portYIELD_FROM_ISR produced no failure, not because the rule is optional but because the ISR was on the other core and the line was never load bearing. Reading a system correctly means knowing what your instrument is pointed at.
