01 · Overview

What this system does

A radar return comes in as a hardware interrupt. The ISR does the minimum work it is allowed to do, which is the timestamp, the debounce gate, and the signal. It then hands the actual response off to a lower priority task. Four periodic avionics tasks keep running on the same core the whole time. The question this bench answers is what actually delays the response, the signaling mechanism or the priority ladder.

Configuration under test

  • Button on GPIO 18, internal pull-up, negative edge interrupt, 200 µs debounce gate.
  • An IRAM_ATTR ISR raises a scope pulse on GPIO 19, timestamps entry, and signals two bottom halves. One uses a binary semaphore and one uses a direct task notification, so both paths can be compared on the same event.
  • Both bottom half tasks run at priority 12, pinned to Core 1.
  • Four periodic load tasks pinned to Core 1 on a rate-monotonic ladder. Priorities are 15 / 10 / 5 / 2 and periods are 100 / 200 / 500 / 1000 ms.
  • Two compile time switches. WITH_LOAD brings the load fixture online and BREAK_YIELD removes the context switch request from the ISR.

The priority geometry is the whole point. Load task A at priority 15 is the only task in the fixture that outranks the bottom halves at 12. B, C and D at 10, 5 and 2 do not. This means only one task in the fixture can delay a wake, and the cost of that delay is bounded by A's own execution time.

Tailoring

Built toward embedded and avionics software roles. That is why the deliverable is evidence instead of features. It has a schedulability argument, three separate timing instruments, a hazard table mapped to real standards, and a fault injection result reported the way it actually came out rather than the way I expected it to.

03 · Architecture

Concurrency and preemption

Core 1 timeline, idle baseline against the loaded case.

Control flow is one hop. The GPIO edge fires the ISR. The ISR timestamps entry into isr_entry_time_us, checks the debounce gate, then calls both xSemaphoreGiveFromISR and vTaskNotifyGiveFromISR before requesting a context switch. Each bottom half unblocks, reads the shared entry timestamp, works out its own wake latency, updates a running maximum, and logs. Nothing else crosses between interrupt context and task context.

There is one thing the diagram does not show. gpio_install_isr_service() is called from app_main, which runs on Core 0, so the interrupt gets allocated on Core 0 while both bottom halves are pinned to Core 1. That makes every wake in this build a cross core wake. It does not change the priority argument, since the bottom halves still contend with the load fixture on Core 1. It is, however, the reason the fault injection in section 05 produces no visible failure.

Engineering analysis

1 · What is in the ISR, and what is not

Kept

  1. int64_t now = esp_timer_get_time(); This is the timestamp read. It is ISR safe, and both the debounce gate and the latency measurement need it.
  2. if (now - last_edge_us < DEBOUNCE_US) return; last_edge_us = now; This is the debounce gate. It rejects contact bounce so that one press counts as one event. It has to run before any signaling, so it stays.
  3. isr_entry_time_us = now; presses_observed++; These are the single word writes that the bottom halves read.
  4. BaseType_t higher_woken = pdFALSE; This is the wake flag the FromISR API requires.
  5. xSemaphoreGiveFromISR(...) and vTaskNotifyGiveFromISR(...) This is what the ISR exists to do. It flags that work is needed, and these are the ISR safe variants.
  6. portYIELD_FROM_ISR(higher_woken); This requests the context switch on return if a higher priority task became ready. This is also the line I removed for the failure test in section 05.

Removable

  1. gpio_set_level(ISR_PULSE_GPIO, 1/0) Not needed for function. It is only there so the logic analyzer can see ISR entry and exit. It costs about 13 µs of pulse width and would come out of a shipping build.

Not included

  1. No printf or ESP_LOGI. Logging takes a UART mutex, and taking a mutex from an ISR is undefined behavior.
  2. No I2C or other bus reads, since those block for milliseconds.
  3. No malloc, no vTaskDelay, no heavy computation. All of that belongs in the bottom half, which is the entire reason this pattern exists.

2 · Binary semaphore against direct task notification

The reported maximums say notification wins easily, 30 µs against 2560 µs when idle. That comparison does not hold up though, and the instrumentation is the reason why.

Both bottom halves subtract from the same isr_entry_time_us. They run at the same priority, so they go one after the other, and whichever one runs second has the other task's ESP_LOGI sitting inside its measured window. A UART print is not free.

The idle run makes this clear. Notification holds 20-30 µs across all 51 presses, while the semaphore column scatters across 915, 1138, 2381, 2387, 2537 and 2560 µs. A real mechanism cost would be close to constant. It would not spread over 1.6 ms on an otherwise idle core. Then at hits #49 and #50 of the loaded run the order flips, and notification becomes the path reading 2246 µs while the semaphore reads 151 and 416 µs.

So the real wake latency is 20-30 µs on both paths, and the difference between the two mechanisms is smaller than what this instrument can resolve. Direct notification should still be cheaper in principle, since it writes the target task's notification value directly instead of going through a separate queue object, but this bench cannot show that. Claiming an 85x advantage from these numbers would be wrong. To measure it properly I would need per path timestamps and the log moved outside the timed window.

3 · Latency under load, and which task is responsible

Notification's worst case goes from 30 µs idle to 2692 µs loaded, which is about 90x. The obvious answer is that load task A caused it, since A at priority 15 is the only task in the fixture that outranks the bottom halves at 12.

The measured WCET says that is not possible. A runs for 346 µs. One instance of A cannot produce a 2692 µs delay, since it is short by a factor of about eight. B, C and D at priorities 10, 5 and 2 cannot preempt the bottom halves at all, so they contribute nothing.

So the worst case blocking the load fixture can cause is bounded by CA = 346 µs. The remaining 2.3 ms or so is the same print order problem from question 2. It shows up in the loaded run for the same reason it shows up when idle.

There is separate evidence that the ladder is working the way it is supposed to. While presses are happening, the measured times for B, C and D go up. B goes from 15238 to 23315 µs, C from 33368 to 41887, and D from 100011 to 108528. A stays at exactly 346 across four separate runs. That is the priority order showing up directly in the data. MEASURE_WCET brackets wall clock time, so for B, C and D it counts preemption by the priority 12 bottom halves as if it were execution time. Nothing in this system preempts A, so A's number is a true WCET while the other three are response times with interference included. The table above reports the quiescent values.

4 · Induced failure

Covered in section 05 below.

Two instruments, two different windows

The 15.35 µs from the logic analyzer and the 20-30 µs from the serial log are not measuring the same thing, so they should not be expected to match. The analyzer spans button edge to ISR pulse, which covers hardware edge detection, the debounce comparison, and the ISR prologue. The serial number spans ISR entry to the bottom half actually running. The first one is interrupt response. The second one is wake latency.

The analyzer number repeats down to the hundredth of a microsecond across three presses because the simulator models the interrupt entry path with fixed timing. On real hardware this would be a distribution, spread out by cache state, bus contention and pipeline effects. The precision here is a property of Wokwi. It is not evidence of a deterministic interrupt path.

05 · Fault injection

Removing the yield

Building with BREAK_YIELD 1 makes the ISR return without requesting a context switch, after a FromISR call has already set higher_woken.

Rule broken. I removed portYIELD_FROM_ISR(higher_woken) after a FromISR primitive had already reported that a higher priority task became ready.

Predicted. The wake gets delivered but nothing acts on it until the next scheduler tick, which turns a microsecond scale response into a millisecond scale one.

Observed. Nothing changed. Per press latency stayed at 24-30 µs and the reported maximum stayed at 2692 µs, which is identical to the build with the yield in place.

They do not match, and core placement is the reason. gpio_install_isr_service() runs from app_main, which is on Core 0, so the interrupt gets allocated on Core 0. Both bottom half tasks are pinned to Core 1. A local yield request only affects the core the ISR is running on. Waking a task on the other core does not use it. ESP-IDF raises an interprocessor interrupt against Core 1, and Core 1 reschedules whether or not portYIELD_FROM_ISR was called. In this configuration that line is dead code, which is why taking it out changes nothing.

How to make the failure visible. Install the ISR service from a task pinned to Core 1, so the interrupt and its bottom halves are on the same core. The yield then actually governs the wake, and removing it should push the response out to the next tick. That is a prediction and not a measurement. The build on this site keeps the original Core 0 placement, and testing this is the first thing I would do next.

08 · Reflection

Looking back

Draft below, built from what actually happened during this build. Rewrite it in your own voice before you ship it. This is the section a reader is most likely to notice you did not write.

What I would do differently

I would instrument it once, correctly, instead of interpreting around a flawed measurement. Both bottom halves share one entry timestamp and both log inside the timed window, and that single decision cost me the comparison the whole application exists to make. I spent more effort explaining why the semaphore number was not real than it would have taken to latch two separate timestamps and move the print. I would also check that the documented periods matched the code before building an analysis on top of them. The comments say 10 / 20 / 50 / 100 ms and the firmware says 100 / 200 / 500 / 1000, which is a factor of ten. If I had trusted the comments my utilization would have come out at 2.46 and the whole task set would have been infeasible.

What was harder than expected

Trusting arithmetic over an explanation that already sounded right. My first analysis blamed a 2692 µs delay on the priority 15 load task, which is clean and fits the priority ladder exactly. Then I measured that task's execution time at 346 µs and the explanation stopped being possible. The number I had been most confident about was the one that was wrong, and nothing about the reasoning felt weak until I checked it against a measurement.

The most valuable thing I learned

A measurement is a claim about one specific window, and most of the work is knowing which window you are looking at. The logic analyzer reads 15.35 µs and the serial log reads 20-30 µs for what I was loosely calling the same thing, and both are correct, because they bracket different events. The fault injection taught the same lesson. Removing portYIELD_FROM_ISR produced no failure, not because the rule is optional but because the ISR was on the other core and that line was never load bearing. Reading a system correctly means knowing what your instrument is actually pointed at.
